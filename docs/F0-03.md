# F0-03 — Corrección y reapertura de ventas

## Reglas y uso

Desde **Ventas → Ver / gestionar** se consulta el historial y se accede a:

- **Corregir venta:** permite cambiar comprador, precio final, agente, porcentaje
  total, reparto del agente, fecha del cierre y notas. El motivo es obligatorio.
  Conserva la propiedad y la identidad de la operación, que sigue vendida.
- **Reabrir venta:** requiere motivo y estado de destino. Desactiva el cierre y
  revierte su efecto económico. El cierre anterior conserva sus datos y puede
  consultarse en «Ventas reabiertas» o «Todo el historial». Para cambiar las
  condiciones tras reabrir se registra un nuevo cierre con los nuevos datos.

El agente asignado actualmente a la propiedad puede gestionarla. `MANAGER` y
`ADMIN` pueden gestionar todas las propiedades de su agencia. La selección de
comprador y agente mantiene los permisos y datos obligatorios de F0-02. El cambio
de agente en la venta modifica la atribución económica; la asignación de la ficha
sigue gestionándose por su operación específica.

| Origen | Operación | Resultado |
| --- | --- | --- |
| Cualquier estado distinto de Vendida, sin cierre activo | Cerrar venta | Vendida, venta activa y comisión |
| Venta activa | Corregir | Vendida, nueva versión y ajuste de comisión |
| Venta activa | Reabrir | Estado elegido distinto de Vendida, venta inactiva y reversión de comisión |
| Venta reabierta | Nuevo cierre | Nueva operación con sus datos; historial anterior conservado |
| Vendida | Cambio genérico a otro estado | Rechazado: requiere reapertura |
| Otro estado | Cambio genérico a Vendida | Rechazado: requiere cierre completo |

Una venta reabierta no puede corregirse ni reabrirse otra vez: se consulta como
historial y sus nuevas condiciones se introducen en el siguiente cierre. Los
cierres activos históricos duplicados se rechazan con explicación y se mantienen
para revisión; no se eliminan ni se elige uno automáticamente.

## Comisiones y liquidaciones

Las comisiones forman un registro de movimientos con importes positivos y
negativos. Una corrección añade la diferencia entre la comisión que corresponde
ahora y lo ya registrado. Una reapertura deja en cero el devengo de esa venta.
No se reescriben los importes, las fechas ni las referencias de pagos previos.
Los ajustes nacen pendientes, también si el movimiento anterior está facturado.

| Situación | Movimiento añadido | Saldo resultante |
| --- | --- | --- |
| Comisión pendiente de 2.400 €, corregida a 1.800 € | −600 € | 1.800 € pendientes |
| Comisión pagada de 2.400 €, corregida a 1.800 € | −600 € | 600 € a favor de la agencia |
| Venta reabierta con 2.400 € ya pagados | −2.400 € | 2.400 € a descontar o recuperar |
| Después del caso anterior se devengan otros 3.600 € | +3.600 € | 1.200 € pendientes de pago |
| Se cambia de agente | Reversión al anterior y abono al nuevo | Cada agente conserva su propio saldo |

**Comisiones → Saldos pendientes** agrupa todos los movimientos abiertos por
agente. «Liquidar saldo» incluye automáticamente los descuentos de ventas
anteriores. Un saldo negativo puede quedar pendiente para descontarse de futuras
comisiones; «Registrar devolución» se confirma cuando la agencia haya recibido el
importe. Un saldo cero se puede compensar sin transferencia de dinero.

La liquidación guarda su importe neto, movimientos incluidos, autor, fecha,
referencia y notas. El historial muestra el importe neto de la liquidación junto
a cada movimiento incluido. «Liquidada» significa saldada por pago, devolución o
compensación; el importe neto permite distinguir los casos. Una factura previa no
se sustituye al liquidar. Las facturas se registran sobre movimientos concretos.

Los indicadores de ventas, volumen, reparto, clasificación de agentes y series
de informes usan solamente cierres activos. El historial de comisiones incluye
los cierres reabiertos y sus ajustes, porque conserva pagos y saldos pendientes.
Las definiciones generales de indicadores de F0-04 siguen fuera de este cambio.

## Trazabilidad y consistencia

- Cada cierre, corrección y reapertura registra autor, fecha, motivo, versión y
  valores anteriores/nuevos. Los importes del historial se guardan como cadenas
  decimales exactas. No hay endpoints para editar ni borrar eventos.
- Una corrección/reapertura incluye `expected_version` y un `request_id` único.
  El mismo intento se puede repetir sin otro ajuste. Reutilizarlo con otros datos,
  o enviar una versión antigua, devuelve `409` con explicación.
- La venta, la propiedad, su evento y los ajustes se guardan en una transacción.
  Los cambios económicos se serializan por agencia, antes de bloquear la propiedad
  y la venta. Esto impide que una liquidación omita una corrección concurrente.
  Es una opción deliberadamente sencilla para Fase 0; limita el paralelismo de
  escrituras económicas dentro de una misma agencia.
- La liquidación exige el `balance_token` recibido al consultar pendientes y su
  propio `request_id`. Si el saldo o sus facturas cambian, se debe recargar antes
  de confirmar. Un reintento ya confirmado devuelve la liquidación original.
- Todas las nuevas escrituras requieren sesión, permisos de agencia y token CSRF.

## Contrato de API

| Ruta | Uso |
| --- | --- |
| `GET /properties/sales/list?state=active\|reopened\|all` | Listado; por defecto solo activas |
| `GET /sales/{id}` | Venta, historial y movimientos de comisión |
| `POST /sales/{id}/correct` | Datos obligatorios de F0-02, fecha con zona horaria, motivo, versión e identificador del intento |
| `POST /sales/{id}/reopen` | `target_status`, `reason`, `expected_version`, `request_id` |
| `GET /commissions/pending` | Saldo completo y `balance_token` por agente |
| `POST /commissions/agents/{id}/settle` | `balance_token`, `request_id`, `payment_date`; factura y notas opcionales |
| `POST /commissions/entries/{id}/invoice` | Referencia de factura y notas del movimiento |

Las antiguas rutas de pago/facturación por venta devuelven `409` e indican el
nuevo flujo. Una venta ahora puede tener varios movimientos y agentes; seleccionar
silenciosamente el primero permitiría omitir descuentos o alterar otra comisión.
El frontend y el backend deben actualizarse juntos.

## Migración y datos existentes

La revisión `f003a1b2c3d4` sigue a `f002a1b2c3d4`. Añade actividad y versión a las
ventas, tablas de eventos y liquidaciones, y referencias en los movimientos de
comisión. Sustituye la comisión única por venta por un registro de movimientos.

Los cierres existentes se consideran activos y de versión 1. No se inventan
actores ni motivos históricos. Su primera modificación conserva una instantánea
de los valores anteriores. No se modifican las cantidades ni los pagos existentes,
incluidas sus fracciones de céntimo heredadas. Las nuevas condiciones de venta se
calculan con el redondeo decimal de F0-02.

Si falta un movimiento histórico, una corrección reconcilia lo registrado con el
importe debido creando una comisión pendiente; no presume que se haya pagado. Una
reapertura revierte solo los importes efectivamente registrados. El inventario de
inconsistencias funciona antes y después de la migración y distingue el historial
reabierto de los cierres activos duplicados.

Para actualizar una instalación, con copia de seguridad previa, desde `backend/`:

```bash
uv sync --locked
uv run --locked python -m scripts.audit_sales
uv run --locked alembic upgrade head
uv run --locked python -m scripts.audit_sales
```

La migración se ha probado en PostgreSQL aislado. El usuario confirma que la ha
aplicado a la instalación y que el funcionamiento parece correcto.
Si ya hay eventos o liquidaciones, el downgrade se
rechaza antes de borrar historia; cualquier vuelta atrás debe planificarse con una
copia revisada. Si aún no se ha usado la funcionalidad, se puede revertir.

comisiones pendientes/facturadas/pagadas, cambio de agente, ajustes sucesivos,
reapertura y nuevo cierre, saldo negativo y compensación a cero, reintentos,
escrituras simultáneas, rechazo de datos antiguos, atomicidad, CSRF, historial,
inventario y protección del downgrade. Los formularios, sus validaciones y las
liquidaciones se prueban en un DOM simulado. Resultado: **113 pruebas backend y
31 de interfaz superadas**, además de la compilación de producción y comprobaciones
de estilo de los componentes nuevos. Se revisaron en Chrome sin interfaz gráfica
el historial, la corrección (escritorio y móvil), la reapertura, los saldos y la
devolución, usando respuestas de API ficticias. Esta revisión visual no sustituye
una prueba completa de navegación contra la instalación desplegada.
