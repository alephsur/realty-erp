# F0-05 — Permisos e integridad entre entidades

Implementada el 16/09/2026. **No requiere migración.** Backend y frontend deben
actualizarse juntos: las bajas de clientes y empleados conservan ahora los registros.

## Reglas de acceso

| Operación | Agente | Administrador o gerente |
|---|---|---|
| Consultar propiedades y clientes | Solo su cartera asignada | Todos los de su agencia |
| Crear y editar clientes | Clientes propios; sin reasignar ni archivar | Puede asignar, reasignar, archivar y restaurar |
| Crear, editar, asignar o eliminar propiedades | No | Sí; la eliminación requiere ausencia de historial comercial |
| Registrar y gestionar visitas | Visitas propias con propiedad y cliente accesibles | Visitas de su agencia |
| Consultar coincidencias e intereses | Solo referencias de su cartera | Referencias de su agencia |
| Gestionar empleados | No | Usuarios de su agencia; nunca superadministradores |
| Consultar resumen global y clasificación de agentes | No | Sí |
| Cerrar, corregir y reabrir ventas | Se mantienen las reglas de F0-02 y F0-03 | Se mantienen las reglas de F0-02 y F0-03 |

El superadministrador gestiona agencias desde sus rutas específicas; no adquiere
acceso a la operativa comercial por enviar identificadores de una agencia.
Un usuario de agencia no puede convertirse en superadministrador. Los permisos
se obtienen del usuario actual en la base de datos, no de un rol antiguo del token.

Las cuentas y agencias inactivas no pueden iniciar sesión ni seguir utilizando
una sesión anterior. Desactivar un empleado invalida sus invitaciones pendientes.
La agencia debe conservar al menos un administrador o gerente activo.

## Asignaciones y referencias

- El agente asignado debe existir, estar activo y pertenecer a la misma agencia.
  Puede tener rol de agente, administrador o gerente.
- Un agente no puede crear registros a nombre de otro usuario ni reasignar clientes.
- Una visita requiere una propiedad accesible. Si incluye cliente, debe ser un
  demandante activo y accesible. Cuando la gerencia asigna la visita a un agente,
  ambos registros también deben ser accesibles para ese agente.
- Los intereses requieren un demandante activo y una propiedad accesible;
  se rechazan duplicados y referencias inexistentes o ajenas.
- No se cambia el tipo de un cliente que ya participa en visitas, intereses o ventas.
- La asignación masiva valida todo el lote antes de guardar. Si un identificador
  no es accesible, no modifica ninguna propiedad.
- Los identificadores y los datos temporales de visitas inválidos se rechazan como
  errores de entrada. Las escrituras revisadas exigen el token CSRF de la sesión.

La asignación actual determina la visibilidad. Si una propiedad o un cliente pasa
a otro agente, el anterior deja de ver las visitas que contienen esa referencia,
también en listados, contadores, calendario, exportación iCal y avisos de conflicto.
El nuevo agente no hereda automáticamente las visitas del anterior: la gerencia
mantiene su consulta. No se reescribe el agente histórico de visitas ni ventas.
Las notificaciones ya recibidas conservan el texto histórico; sus enlaces aplican
los permisos actuales al abrir el registro.

Las asignaciones, las bajas y las escrituras económicas comparten un bloqueo por
agencia. Una venta que espera a una reasignación vuelve a comprobar los permisos
antes de cerrarse. Esto prioriza coherencia; las escrituras de una misma agencia
se procesan secuencialmente durante su transacción.

## Bajas e historial

- **Clientes:** `DELETE /clients/{id}` archiva mediante `is_active=false`.
  Se conservan visitas, intereses, ventas y el comprador histórico. El listado
  muestra clientes activos por defecto; «Incluir clientes archivados» permite
  consultar los demás. La gerencia puede restaurarlos o reasignarlos.
- **Empleados:** la baja desactiva el acceso y conserva asignaciones y atribución
  de ventas y comisiones. La interfaz permite generar una nueva invitación para
  reactivar el acceso. Los empleados inactivos no aparecen en nuevas asignaciones.
- **Propiedades:** no se pueden eliminar si tienen visitas, intereses o ventas,
  incluidas ventas reabiertas. Se devuelve una explicación y se conserva el registro.
  Una propiedad no vendida se puede retirar mediante su estado.
- **Agencias:** no se eliminan agencias con propiedades o clientes. La gestión
  permite desactivarlas conservando sus datos.

Archivar o reasignar no cambia importes, pagos, facturas ni eventos de venta.
Las correcciones y reaperturas económicas siguen realizándose por sus operaciones
específicas, con los ajustes de comisión definidos en F0-03.

## Datos anteriores

Las validaciones protegen la API; no sustituyen controles en una importación SQL
externa. No se reparan ni eliminan silenciosamente referencias antiguas. Las
consultas de clientes, propiedades y visitas revisadas excluyen referencias
directas que cruzan agencias.

Se incorpora un inventario de solo lectura para detectar referencias antiguas
entre agencias y superadministradores asociados incorrectamente a una agencia:

```bash
# Desde backend/, con acceso de lectura a las agencias que se quieran comprobar:
uv run --locked python -m scripts.audit_entity_integrity
```

Devuelve identificadores, sin datos de contacto. Termina con código `1` si encuentra
inconsistencias y `0` si no las encuentra. Las asignaciones a empleados inactivos
son válidas como historial. Este inventario complementa `scripts.audit_sales`;
no analiza todas las reglas comerciales ni modifica datos.

## Validación

Las pruebas utilizan PostgreSQL desechable y sesiones HTTP reales. Cubren la matriz
de roles, accesos entre agencias, asignaciones inválidas, referencias de visitas e
intereses, elevación de permisos, bajas, invitaciones revocadas, conservación del
historial económico, reasignaciones concurrentes con cierres y el inventario de
inconsistencias. Se mantienen las pruebas de F0-02, F0-03 y F0-04.

La interfaz comprueba archivo/restauración, edición del agente sin reasignación,
selección de empleados activos y filtrado de referencias al programar una visita.

```bash
# Desde backend/, sin utilizar el entorno de la instalación:
UV_PROJECT_ENVIRONMENT=/tmp/realty-permissions-check uv sync --locked
RUN_POSTGRES_TESTS=1 UV_PROJECT_ENVIRONMENT=/tmp/realty-permissions-check uv run --locked pytest -q --disable-warnings

# Desde frontend/:
npm test
npm run build
```

Resultado: **194 pruebas backend y 40 de interfaz superadas**, compilación de
producción correcta y revisión visual en Chrome con respuestas de API ficticias.
No se ha modificado la base de datos de la instalación. Esta revisión visual no
sustituye una prueba completa contra el despliegue.

La automatización del recorrido completo y su integración como condición de entrega
corresponden a F0-06.
