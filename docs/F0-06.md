# F0-06 — Comprobaciones automáticas del flujo comercial

Implementada el 16/09/2026. No requiere migración ni cambios en los datos
existentes. Incluye el workflow de GitHub Actions; los resultados remotos de cada
revisión se consultan en Actions, además de la validación local documentada.

## Recorridos comprobados

Cinco pruebas en Chromium, con la compilación de producción, una API real y
PostgreSQL 15 independiente. Las respuestas comerciales no se simulan.

1. Un visitante sin sesión vuelve al login; una contraseña incorrecta no permite
   acceder. Se verifica también la respuesta CORS de `/auth/login`.
2. La gerencia crea una propiedad, registra y asigna un demandante, programa una
   visita, la marca como realizada y cierra desde **Propiedades**. Comprueba venta,
   comprador, agente, estado del inmueble y comisión. Corrige el precio, verifica
   el ajuste de comisión y reabre, comprobando el descuento y los tres eventos.
3. La gerencia repite el recorrido cerrando desde **Pipeline**.
4. La gerencia repite el recorrido cerrando desde **Ventas**.
5. Un agente registra un demandante, realiza una visita y cierra su propiedad
   asignada; no puede consultar propiedades de otra agencia ni abrir Comisiones.

En el modelo actual, la creación de oportunidad se representa con el inmueble
captado y el cliente demandante. Estas pruebas no introducen un módulo independiente
de oportunidades, ofertas o leads.

El acceso utiliza el formulario y las cookies reales. Se comprueban la persistencia
tras recargar, la cookie de acceso `httpOnly`, el token CSRF y el cierre de sesión.
Las escrituras pasan por la interfaz; las comprobaciones finales leen la API con la
misma sesión para confirmar lo que se guardó. Un error JavaScript no controlado
hace fallar la prueba. Se ejecuta un único navegador a la vez, sin reintentos
automáticos que oculten fallos, y se rechazan pruebas omitidas o marcadas como `only`.

Se asociaron etiquetas a los campos utilizados y se dio un nombre accesible al
menú de usuario. Esto mejora el uso del formulario y permite seleccionar controles
por su significado, sin depender de su posición en pantalla.

## Ejecución local

Requisitos: Linux o WSL con Python 3, `uv`, Node 24, npm y acceso a Docker. El ejecutor
usa Python 3.12 para la API. Las dependencias del proyecto y Playwright están fijadas
en sus archivos de bloqueo.

```bash
# Desde frontend/, una vez al preparar el entorno:
npm ci
npx --no-install playwright install --with-deps chromium

# Cada comprobación completa del navegador:
npm run test:e2e
```

El comando:

- Crea un contenedor y una base con nombre exclusivo, contraseña aleatoria y puerto
  local libre. Siempre genera su propia `DATABASE_URL`.
- Aplica las migraciones y prepara dos agencias ficticias, usuarios y propiedades
  de prueba. El preparador rechaza destinos ajenos al ejecutor y bases con datos.
- Crea por defecto un entorno Python temporal, compila el frontend en una carpeta
  temporal y arranca servicios propios en puertos libres. No reutiliza la API ni
  el frontend que estén abiertos, ni modifica `.env` o el `dist` habitual.
- Ejecuta los cinco recorridos y propaga los fallos como código de salida distinto
  de cero. Un informe vacío, ausente, con fallos u omisiones tampoco es válido.
- Detiene sus procesos y elimina su contenedor y volúmenes al terminar, también
  cuando una prueba falla o se interrumpe normalmente.

Se puede reutilizar un entorno Python **de pruebas** configurando
`UV_PROJECT_ENVIRONMENT=/tmp/realty-checks` antes del comando. No es necesario
utilizar el `.venv` de la instalación.

Para depurar solo un recorrido:

```bash
npm run test:e2e -- --grep 'assigned agent'
```

Esa selección sirve para diagnóstico; una entrega requiere la suite completa.
Para ver el navegador, añadir `--headed` en un entorno con pantalla gráfica.

## Resultados y diagnóstico

Cada ejecución conserva una carpeta `frontend/e2e-artifacts/<identificador>/` con:

- `results.json`: resultado estructurado de las pruebas.
- `report/`: informe HTML navegable.
- `backend.log` y `frontend.log`: salida de los servidores de prueba.
- `test-results/`: capturas, vídeo y traza cuando una prueba falla.

El comando imprime la ruta exacta. Se puede abrir el informe con
`npx --no-install playwright show-report e2e-artifacts/<identificador>/report`,
siempre desde `frontend/`. Son diagnósticos de datos ficticios y no se incluyen
en Git. El almacenamiento y la visualización de trazas siguen la
[documentación de Playwright](https://playwright.dev/docs/test-configuration).

## Control de entrega en GitHub

El workflow `.github/workflows/quality.yml` se ejecutará en pull requests, pushes
a `main` y lanzamientos manuales. Usa dependencias bloqueadas y acciones fijadas
por revisión, sin credenciales de la instalación.

| Control | Condición para aprobar |
|---|---|
| Backend and PostgreSQL | Toda la suite backend, con PostgreSQL real y sin pruebas omitidas |
| Frontend tests and production build | Pruebas de interfaz sin omisiones, TypeScript y compilación de producción |
| Critical browser flows | Los cinco recorridos completos contra servicios y datos desechables |
| **Delivery gate** | Los tres controles anteriores han terminado correctamente |

`Delivery gate` también rechaza controles cancelados u omitidos. Los informes se
conservan como artefactos durante siete días. `scripts/check_test_results.py`
comprueba los informes del backend y de la interfaz; tiene pruebas que verifican
el rechazo de informes con errores, fallos, omisiones, vacíos, ausentes o inválidos.

**Estado de GitHub comprobado:** `main` no tiene protección de rama. Un workflow
fallido marca la entrega como no válida, pero por sí solo no bloquea una fusión.
Después de publicar esta fase y ejecutar el workflow, se debe exigir el estado
**Delivery gate** en la protección o las reglas de `main` para bloquear fusiones
que no lo superen. No se han cambiado las reglas remotas del repositorio.

## Validación de esta implementación

- Cinco pruebas del navegador superadas contra los servicios reales de prueba.
- **204 pruebas backend y 40 de interfaz superadas**, sin omisiones; compilación
  de producción correcta.
- Workflow validado con `actionlint`; scripts Python y pruebas nuevas revisados
  con Ruff/ESLint y comprobación de tipos.
- Verificado que un fallo de prueba devuelve error y conserva sus diagnósticos;
  los contenedores E2E se eliminan al finalizar.
- La instalación del usuario no se ha utilizado como destino de estas pruebas.

La fase 0 dispone así de una comprobación automática del recorrido comercial
actual. La validación con las agencias piloto y la elección de integraciones de
la fase 1 siguen siendo decisiones de producto.
